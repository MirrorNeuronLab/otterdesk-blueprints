# Claim-to-evidence traceability

**Section:** 21 · Evidence and confidence  
**Specification ID:** `AR-21-08`  
**Customer question:** Can every conclusion, recommendation, and work package be traced back to verifiable observations?

## What to include

- Assign stable IDs to claims, evidence, findings, recommendations, validation tasks, and work packages.
- Link each material claim to the exact evidence that supports it and describe the relationship.
- Connect summaries and recommendations to their detailed canonical findings instead of duplicating unsupported claims.
- Record version, scope, status, and supersession so readers can detect stale or conflicting artifacts.

## Why this matters

Traceability makes the architecture report auditable and maintainable. Customers can challenge a premise, inspect the source, and see which decisions would need to change if the premise is rejected.

## Evidence to use

Use all canonical evidence and finding registers with real, versioned locators. Report unresolved links as completeness gaps.

## Expected report output

A traceability register linking evidence to claims, findings, actions, validation, and implementation tasks, with clear provenance.

## Completion and quality checks

Every link must resolve to an actual artifact or explicitly unavailable source. Do not invent citations, treat repeated summaries as independent evidence, or hide unsupported claims behind a general bibliography.

Apply the [shared report conventions](../REPORT_CONVENTIONS.md), including
claim-level traceability, confidence, scope, and explicit handling of missing
evidence. This file specifies required content; it does not assert that an
analysis or test has already been performed.
