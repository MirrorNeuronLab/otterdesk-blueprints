# Hiring and onboarding complexity

**Section:** 20 · Business impact  
**Specification ID:** `AR-20-07`  
**Customer question:** How does the architecture affect the effort required for a new contributor to become effective?

## What to include

- Identify the knowledge, environment setup, services, implicit contracts, and cross-team dependencies needed for representative starter tasks.
- Assess documentation, test feedback, local development, and boundary clarity using observable evidence.
- Distinguish architectural obstacles from missing training or general organizational process.
- Define improvements and an onboarding measure or task-based evaluation to test their value.

## Why this matters

Customers need to know whether understanding a small change requires learning the entire system. A task-based view makes onboarding improvements concrete without reducing people to productivity metrics.

## Evidence to use

Use development setup instructions, dependency requirements, representative changes, documentation coverage, and stakeholder-supplied onboarding observations.

## Expected report output

An onboarding-friction table with task, required knowledge, obstacle, evidence, proposed improvement, and evaluation method.

## Completion and quality checks

Do not infer hiring difficulty from the number of languages or tools alone. Avoid invented time-to-productivity estimates and distinguish documented setup from a setup actually tested.

Apply the [shared report conventions](../REPORT_CONVENTIONS.md), including
claim-level traceability, confidence, scope, and explicit handling of missing
evidence. This file specifies required content; it does not assert that an
analysis or test has already been performed.
