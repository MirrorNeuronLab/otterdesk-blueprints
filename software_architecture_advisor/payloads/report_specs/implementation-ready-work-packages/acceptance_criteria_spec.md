# Acceptance criteria

**Section:** 23 · Implementation-ready work packages  
**Specification ID:** `AR-23-07`  
**Customer question:** What objective evidence allows this task to be accepted?

## What to include

- Define observable outcomes tied directly to the task goal and architectural constraints.
- Include relevant functional, structural, data-correctness, operational, and documentation conditions.
- Specify the evidence artifact or review method for each condition and who accepts it.
- State handling for unmet conditions, exceptions, residual risks, and follow-up tasks.

## Why this matters

Customers and implementers need the same definition of done. Evidence-based acceptance prevents completion from being reduced to a merged patch while the intended architectural property remains unverified.

## Evidence to use

Use the approved task goal, validation plan, required tests, constraints, and migration exit gates.

## Expected report output

A pass/fail acceptance checklist with criterion, evidence requirement, result, reviewer role, and exception status.

## Completion and quality checks

Criteria must be testable and within the task’s control. Do not invent business outcome guarantees or use vague conditions such as code is clean or architecture is better.

Apply the [shared report conventions](../REPORT_CONVENTIONS.md), including
claim-level traceability, confidence, scope, and explicit handling of missing
evidence. This file specifies required content; it does not assert that an
analysis or test has already been performed.
