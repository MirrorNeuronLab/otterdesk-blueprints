# Recommended action

**Section:** 18 · Concrete prioritized recommendations  
**Specification ID:** `AR-18-04`  
**Customer question:** What specific change or investigation should the customer undertake?

## What to include

- State the proposed action and the architectural property it is intended to improve.
- Define scope, affected components, constraints, non-goals, and prerequisites.
- Explain why this action addresses the identified mechanism and compare a smaller alternative where relevant.
- Identify the owner role, major risks, reversibility, and linked migration or work-package details.

## Why this matters

Customers need a next move rather than a list of symptoms. Connecting action to mechanism makes the advice easier to review and prevents generic refactoring from expanding beyond the problem.

## Evidence to use

Use the finding, alternative analysis, dependency and data impacts, implementation feasibility, and supplied operating constraints.

## Expected report output

An action card with action verb, scope, rationale, prerequisites, constraints, owner status, risks, and references to execution details.

## Completion and quality checks

Do not prescribe an invasive change when verification is the responsible next step. Mark proposed owners and unapproved changes clearly; the report itself authorizes no implementation.

Apply the [shared report conventions](../REPORT_CONVENTIONS.md), including
claim-level traceability, confidence, scope, and explicit handling of missing
evidence. This file specifies required content; it does not assert that an
analysis or test has already been performed.
