# CCTV Operator user manual

Version3.1: choose site.profile=factory or hotel. An omitted/blank monitoring goal uses the selected profile. Independent person triggers and periodic scene audits cover sampled activity and static hazards; forecasts remain hypotheses. Review the facility queue, evidence and unexamined rules in the report/status. One approved common-area camera per Job. Named rectangles are not privacy masks. No identity, medical, compliance or autonomous-response conclusions.


Tell it what to watch for on your camera feed. Get alerts with images and times you can review, and ask questions about previously reviewed footage.

## Inputs

- alert_policy: Cooldown, confidence, and notification policy for reviewer notices.
- attention_instruction: Operator instruction for a detail to watch in the current stream.
- output_folder: Default local output folder for generated artifacts and reports.
- slack_destination: Optional approved Slack destination for alert delivery.
- video_source: Bundled Docker demo stream by default, or one approved external RTSP/RTMP URI.
- visual_targets: Configured subjects, objects, or activities to detect.
- demo_file: Local warehouse demo MP4 staged from the submitting computer, used only in bundled_demo profile.
- monitoring_goal: Visible event condition that triggers a chat report with capture time and a frame.

## Domain tools

- `get_operator_status`: Read the latest Cosmos scene understanding and its timestamp, plus separate RF-DETR person-gate and Cosmos health. RF-DETR only gates person presence; it never judges helmets or creates Chat findings. The gate cannot be changed. Questions do not change monitoring.
- `get_operator_activity`: Read existing observations only; this does not change what the vision model looks for. after_revision must be a non-negative integer: use 0 for available history or a returned revision for subsequent updates. Never use "latest".
- `watch_job_activity`: Wait for the next confirmed monitoring-goal event without changing the goal. Quiet and unrelated activity produce no chat messages. Use an empty after_event_id for the newest event or the returned ID, and a native numeric wait_seconds from 0 to 25.
- `set_monitoring_instruction`: Change the ongoing Cosmos analysis goal only when the operator explicitly asks to change the goal, keep watching, focus on, or alert about a future visible condition. Examples: "change the goal to watch the corridor for obstructions" and "can you focus on find foreign object on the floor?". A retrospective question such as "can you find if anyone did not wear a helmet?" is a history read: use answer_video_question, never this tool. RF-DETR remains the fixed person detector; configured periodic scene audits can also inspect static hazards without a person. Put the requested analysis goal in instruction, clear=false, analyze_now=true. A new analysis waits for an eligible person-triggered or periodic-audit window, subject to the same admission interval and active-model limit. Restore the saved goal with instruction="", clear=true, analyze_now=true. Report applied only after command status completed; acceptance means queued. Check analysis_ready before presenting a finding.
- `acknowledge_operator_notice`: Mark a specific notice reviewed only when the operator requests acknowledgement. This does not change monitoring focus.
- `get_video_history`: Read up to twelve latest matching authored Markdown camera accounts from job-scoped context memory, including previous runs. Use for what happened and predicted-risk history. after and before are optional ISO 8601 times with timezone, or empty strings. Preserve citations, camera, capture times, source_profile and prediction qualifications; the result is bounded, not exhaustive.
- `get_video_summary`: Summarize this run’s saved Markdown observations in context memory using the text model only. Never retrieve images or invoke Cosmos. This is an asynchronous read; report completion after get_operation_status returns completed. Optional after and before are timezone-qualified ISO 8601 capture times or empty strings. Preserve citations, sampled coverage, recording qualifications and omitted history. Does not change monitoring.
- `answer_video_question`: Answer the actual question from saved authored Markdown for this camera and source across Job runs, using Membrane context memory and the text model only. Use for retrospective questions, including "can you find if anyone did not wear a helmet?". Never change monitoring, retrieve images or invoke Cosmos. This is an asynchronous read; poll get_operation_status for completion. Optional after and before are timezone-qualified ISO 8601 capture times or empty strings. Preserve evidence times, citations, recording qualifications and sampling limits. Missing history does not mean zero people; repeated observations cannot establish unique people or a cumulative total.
- `get_pipeline_benchmarks`: Read retained per-stage timing, p50/p95, errors and skipped coverage for RF-DETR person events, Cosmos captioning, MN memory and historical Q&A. Cold starts and hardware/model cohorts are separate. Notice latency ends at SDK/MCP publication, not desktop receipt.


## Supervision

Use `get_capabilities` for the current tools and their availability. Common MCP actions are implemented by the SDK. `start_run` starts new work, `pause_run` preserves a resumable run, `resume_run` continues it, and `stop_run` terminates it. Domain stop actions affect their named resource only. Accepted actions are not evidence of completion; use `get_operation_status`.

External mutations require a caller-generated `request_id`. Tool results use `mn.mcp.tool_result.v1` in `structuredContent`; keep workflow state inside `data` and poll a returned `operation_id` with `get_operation_status`. The runtime also publishes this installed manual through its MCP Skills manifest.
